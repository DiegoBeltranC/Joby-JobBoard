# Git

## Conventional Commits

All commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>
```

### Types

| Type | When to use |
|---|---|
| `feat` | New feature |
| `fix` | Bug fix |
| `refactor` | Refactor without behavior change |
| `test` | Adding or fixing tests |
| `docs` | Documentation |
| `style` | Formatting/lint, no logic change |
| `chore` | Config, deps, scripts, tooling |
| `ci` | CI/CD changes |
| `perf` | Performance improvement |
| `build` | Build system / dependency changes |

### Scope

Optional but recommended — the affected area/domain. In this project scopes read naturally in Spanish:
`vacantes`, `perfil`, `auth`, `empresa`, `postulaciones`, `cv`, `admin`, `mail`.

```bash
feat(vacantes): agrega filtro por modalidad en el inicio
fix(auth): corrige cooldown de reenvío de OTP
feat(cv): añade optimización de bio con IA
refactor(perfil): extrae cálculo de progreso a lib
chore(deps): actualiza prisma a 6.19
```

### Message rules

- First line ≤ 72 chars.
- Description in the imperative, lowercase first letter, no trailing period.
- Description may be Spanish or English — match the repo's recent history for consistency.

## Atomic commits

Each commit is one complete, functional logical unit. Don't bundle unrelated changes; don't split a
single change into meaningless micro-commits.

```bash
# ✅ per logical unit
git commit -m "feat(vacantes): agrega esquema zod y acción de creación"
git commit -m "feat(vacantes): agrega formulario de nueva vacante"

# ❌ everything at once
git commit -m "feat: cambios varios"
```

## Authorship

Never mention Claude, AI, an assistant, or "generated by" as the author or in the body of a commit.
Commits read as normal human-authored work. (This overrides any global commit-trailer default.)

## Staging

Add only the files relevant to the commit. Prefer explicit paths over `git add .` / `git add -A`, so
unrelated working-tree changes (scratch files, local config) don't leak into the commit.

```bash
git add src/actions/vacantes.ts src/app/empresa/(dashboard)/vacantes/nueva/page.tsx
```

## Branches & Pull Requests

- Default branch is **`main`**. Do routine work on a short-lived feature branch
  (`feat/filtro-vacantes`, `fix/otp-cooldown`) and open a PR into `main`.
- Deployment is **Vercel**: a push/merge to `main` deploys **production**; every PR/branch gets a
  **Preview deployment** automatically. There is no separate long-lived `develop`/`staging`/`v3`
  branch model here — don't invent one.
- Because URLs in emails and QR flows depend on the deploy URL, absolute links must come from
  `NEXT_PUBLIC_APP_URL` / `VERCEL_*` env (see services.md/auth.md), not hardcoded hosts — this keeps
  Preview vs Production correct.
- Keep PRs focused and reviewable; describe what changed and how to test (see
  `.claude/templates/pr-template.md`).

See also: `.claude/templates/pr-template.md`, `.claude/commands/create-pr.md`.
